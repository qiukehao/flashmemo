## 0. 一句话问题

用户想把「闪记」用来**刷题**（LeetCode 式：一道题的题面可能是一段话、一张截图或一段代码），
但发现**手工建卡时正面只能是一行短文本、不能粘贴图片**，于是提出"目前卡片的种类比较少，题目的类型需要再扩展"。
请评审：这里的"题型"应该扩展成什么？先做什么、不做什么？

## 1. 产品背景

**闪记 FlashMemo**：常驻 Windows 托盘的闪卡复习工具。用户导入 Markdown 八股文笔记建卡；常驻引擎每 15 秒评估一次，
到点在屏幕中央弹出复习窗（每次 1~N 张），用户对每张卡三档评分。

- **硬约束**：核心功能零网络请求、数据只在 `%APPDATA%\FlashMemo`、常驻低占用、单实例、将开源（MIT）。
  作者是备考技术面试的学生 + AI 结对开发。
- **用户画像**：备考者。当前笔记几乎全是 MySQL/Redis/JVM/网络 等八股文，**大多数卡片是"一句话问题 + 结构化要点"**。
- **产品哲学**：正向表述（只说"已经做了多少"），目标不变成债务；卡片身份稳定（重导入不能变成新卡）。

## 2. 现状：卡片模型与"出题"的三条路径（真实实现，2026-10-07）

### 2.1 数据模型（`SPEC.md` §14 / `db.rs`）

```
card(
  title      TEXT,   -- 身份键 + 列表标签（单行投影，见 §2.4）
  front_md   TEXT,   -- 题面（正面，Markdown）。空串 = 正面就渲染 title
  content_md TEXT,   -- 要点（背面，Markdown，含批注）
  ... 复习状态: state / due_at / level / unknown_streak / speak_streak / needs_attention ...
)
UNIQUE(chapter_id, title)
```

**注意：`front_md` 已经存在**（2026-10-07 "需求7" 加的），它就是一个完整的 Markdown 字段，
**支持多行、图片、代码块**，弹窗里用与背面同一套渲染器展示（图片走灯箱放大）。
导入幂等键是 `(卡包名, 章节名, 卡片标题)`，**不含 `front_md`**——题面改字不会变成新卡。

**不存在**任何"题型"字段（没有 `kind`，没有 `payload_json`）。

### 2.2 三条"出题"路径，各自能做什么

| 路径 | 正面（题面） | 背面（要点） | 能否"长/图题面 + 结构化答案" |
|---|---|---|---|
| **导入 Markdown** `###` 标题 | `title`，**单行纯文本**（`front_md` 留空） | 标题之下的正文，任意 Markdown | ✗ 正面只能是短标题 |
| **导入 Markdown** `##` 无 `###` 的章节 | **整段内容进 `front_md`**（可多行 / 图片 / 代码块） | **空** | ✗ 有图面就必定没有背面 |
| **手动「添加卡片」页** | 单行 `<input>`，**不能换行、不能粘图** | 多行 textarea，**支持 🖼 按钮与 Ctrl+V 粘图** | ✗ 正面根本放不下题面 |
| **主窗口卡片编辑器** | **只有一行 `input`（编辑的是 `title`）**，`front_md` 既不显示也不可编辑 | contenteditable WYSIWYG，支持图片/批注 | ✗ 题面改不了 |
| **复习弹窗** | 题面**只读**渲染（图片可放大） | 可编辑（WYSIWYG） | 只能"读题面"，不能"改题面" |

（SPEC §5.2 rule 2 / rule 10 定义了上面两条导入路径；"需求7" 的测试名为
`h3_card_has_empty_front_md`、`front_title_projection`。）

### 2.3 一句话总结现状

> **"题面（正面）可以是长文本/图片"这件事，存储和渲染已经实现了；缺的是"手工把题面写成那样"的入口，
> 以及"长/图题面 + 结构化答案"这个组合——现有任何一种路径都做不出来。**

用户说"正面不支持描述题目内容和粘贴图片"，从**手动建卡**的视角看是准确的：
手动加卡页的正面就是一个单行输入框，只有背面能贴图。

### 2.4 身份键对题面的依赖（设计的隐藏约束）

- `title` 是**身份键**，也是所有单行位置（列表行、卡包页、知识铺垫标题、"继续下一张"按钮）的显示来源；
- 对题面卡，`title` 是 `front_md` 的**单行投影**（图片折成 🖼、换行折成 ` · `）；
- 所以**改题面措辞 = 改投影 = 改身份键**。现在靠"同章节内唯一一张题面卡"的回退匹配兜住（SPEC §5.3）。
  这是历史包袱：任何"让用户自由编辑题面"的动作都会踩到它（详见 D2）。

### 2.5 既有评分/调度语义（与题型扩展会冲突的部分）

- 评分是**三档自评**：`不了解 / 熟悉 / 可以讲出来`（SPEC §7）。没有"对/错"这一维。
- 调度是"按再隔几张卡"（全局展示计数 + 熟练等级 0~5 + 时间下限），**不是 FSRS 公式**。
- "掌握/归档" = 连续 3 次「可以讲出来」且跨 3 个不同学习日；"⚠ 重点卡"由连续 3 次「不了解」触发。
- 「跳过」= 30 分钟后重入队。

## 3. 约束红线（请在你的建议中遵守）

- **零网络**：不允许为了"判题"引入任何在线服务。
- **低占用 / 安全**：常驻进程不能因为新题型而做重活（例如：不允许在本进程里跑用户提交的代码）。
- **不破坏既有不变量**：单实例、同一时刻只有一个复习弹窗、每次评分立即落库、卡片身份稳定（重导入不产生新卡）。
- **不破坏既有统计口径**：首页统计 / 热力图 / 连续打卡 / 每日目标 / 疑难 / 归档都按"复习了一次"和"讲出来了一次"记账；
  新增题型若要改这些口径，必须有明确说法。
- **可测试**：解析与调度是纯函数、有单测（`parser.rs` / `scheduler.rs`），新增逻辑也要能脱离 UI 单测。

## 4. 我理解的用户意图

用户原话："目前卡片的种类比较少。我想让它帮我去刷题，LeetCode 这种题目是一段话或者一个图片的不能够设置闪卡，
正面不支持描述题目内容和这个粘贴图片。对于我来说大多数的八股题目其实是只有一个简短的题目，
但是如果想要提高这个软件的普适性，题目的类型需要你再扩展一下。"

拆成两层：

- **(A) 立即的痛点**：手工建卡时，正面要能是一段话 / 一张图 / 一段代码（LeetCode 式"看图说思路"）。
  —— 这一层**只差 UI 入口**，数据模型已经就绪。
- **(B) 普适性诉求**：把"题目类型"本身做成可扩展的（用户没具体说要哪种，只说要"再扩展一下"）。

## 5. 我方困惑（开门见山列出来）

### D1. "题型"到底指哪一档？三种理解，工作量差一个数量级

| 档 | 含义 | 举例 | 需要什么 |
|---|---|---|---|
| **(i) 展示型** | 题面/答案的**形态**更多样 | 题面是长文 / 图片 / 代码块 | **零 schema 变更**，只需编辑入口（正面可写多行 Markdown + 粘图） |
| **(ii) 半交互型** | 有"作答动作"但**不自动判分**，用户自评 | 填空（挖空）、选择题（点完看答案） | 卡表加题型字段 + 载荷 + 弹窗作答 UI + 导入语法 |
| **(iii) 判题型** | 系统判定对错 | 代码判题、自动批改 | 还需语言运行时/沙箱、判分逻辑、评分语义扩展、与三档自评的融合 |

**用户要的是哪一档？** 从"LeetCode / 一段话或一个图片 / 粘贴图片"看，痛点是 (i)；
但"题目的类型需要扩展"又像是指 (ii)。

### D2. 题型化之后，**身份键**怎么算？

现状：`UNIQUE(chapter_id, title)`，题面卡还额外依赖"title = 题面投影"。
若引入 `kind`（basic/cloze/choice/code），会出现：同一道题的**同一标题**，从"普通卡"改成"填空题"会不会变成新卡？
- 选项甲：`kind` 不进身份键 → 改题型保留进度（但也可能让"同一标题的两种题型"无法共存）；
- 选项乙：`kind` 进身份键 → `UNIQUE(chapter_id, title, kind)`，改题型 = 新卡、进度丢失；
- 有没有更好的？（比如题型只是"渲染提示"，真正的差异靠载荷内容推断。）

### D3. 导入语法怎么办？

现规则极简：**只识别 ATX 标题**（`#`/`##`/`###`），其余原样保留（SPEC §5.2）。
若要支持填空题，几乎必然要引入新语法（例如 `{{c1::答案}}` 或 `[[]]`）。
- 这会破坏"只认 ATX 标题"这条规则，也会影响幂等匹配与"围栏代码块内不解析"的既有实现；
- 是否值得？还是应该**只做 (i)**——题面本身就是 Markdown，代码块/图片天然可用，根本不需要新语法？

### D4. 评分语义冲突：三档自评 vs"答对/答错"

判题型需要"对/错"这一维，而现有调度完全建立在三档自评上（`unknown_streak` / `speak_streak` / `level`）。
- 是把判题结果**映射**回三档自评（对→可以讲出来，错→不了解）？还是给调度新增一维？
- 前者简单但语义糊（"答对"≠"能讲出来"）；后者要动 `scheduler.rs` 这个已高度校准的核心。
- 你倾向哪个？如果都不好，是否说明**判题型不该进这个产品**？

### D5. 代码判题与红线冲突

LeetCode 式刷题最想要的是"跑代码判对错"，但：
- 零网络 + 低占用 + 安全 ⇒ 不能在本进程内执行用户代码；
- 引入沙箱/语言运行时 = 巨大复杂度 + 攻击面，与"将开源、学生维护"的定位不匹配。
**是否应把"代码判题"明确排除**，只做"看图/看题写思路 + 三档自评"？

### D6. 弹窗交互够用吗？

弹窗现在：题面**只读**、背面可编辑；评分三档。
LeetCode 式"看一道题，自己说思路，然后对照答案"其实**已经能跑**——只是题面放不下图片/长文。
是否**（A）把题面入口补全**就已经满足 80% 的刷题场景，不需要新题型？

### D7. 若真要做题型，统计/搜索/疑难/归档要不要分题型口径？

SPEC §19 的不做清单已经列过：按题型分口径、搜索按题型筛选、列表按题型过滤……
这些是"题型"的**配套成本**，容易被低估。请评估：不做这些配套，题型能不能单独落地？

### D8. 我倾向的最小可行方案（供评审批判）

**分两期，先做只有收益没有风险的那期：**

**Phase 0（立即可做，零 schema 变更）** —— 把"题面"从导入专用补成**可手工编辑**：
1. 「添加卡片」页：把"问题（正面）"从单行 `input` 换成与背面同款的 Markdown 编辑器（多行 + 🖼 按钮 + Ctrl+V 粘图）；
2. 主窗口卡片编辑器：在标题下方新增**题面区**（可编辑、可粘图），保存走已存在的 `update_card(..., frontMd)` 参数（该参数已实现，只是没人传）；
3. 复习弹窗：题面**保持只读**（避免误编辑），但允许从弹窗"跳主窗口编辑题面"。

这样"长/图题面 + 结构化答案"这个**当前三条路径都做不出的组合**就通了，直接解决 LeetCode 型刷题。

**Phase 1（需要评审拍板，再决定做不做）** —— 真正的题型：
- 若只做 (i) 展示型，其实 Phase 0 已覆盖，无需 `kind`；
- 若要做 (ii) 半交互型，建议从**最小的一种**开始（例如"填空"），且**不自动判分**、仍走三档自评；
- (iii) 判题型 + 代码判题：我倾向**明确排除**（见 D5）。

**请评审**：Phase 0 的取舍对不对？Phase 1 该不该做、做哪一档？有没有我没想到的第三条路
（例如"题型不进数据库，只是一个 Markdown 约定 + 渲染器识别"，从而完全绕开 schema 与身份键问题）？

## 6. 请你回答的问题

1. **D1**：用户口中的"题型"最可能指 (i)/(ii)/(iii) 哪一档？请给出判断依据，并说明你会怎么向用户澄清。
2. **D8/Phase 0**：把"题面"补成可手工编辑（多行 + 图片），是否**足以解决**"LeetCode 式刷题"的核心诉求？
   如果不够，还差什么？
3. **D2**：题型若要落地，`kind` 该不该进身份键？给出一个在"改题型保留进度"与"两种题型共存"之间最优的键设计。
4. **D3**：有没有一种**不需要新导入语法**的题型实现方式（例如纯 Markdown 约定 + 前端渲染器识别挖空/选项）？
   其代价是什么（可测试性、幂等性、用户可预期性）？
5. **D4/D5**：判题型（含代码判题）在这个产品里应该做、还是应该明确排除？如果排除，怎么向用户解释"为什么闪卡不做判题"？
6. **D7**：题型落地的**真实成本**评估——数据库迁移、导入解析、弹窗作答 UI、三档评分融合、统计/搜索/归档口径。
   请给出你认为**不可省略**的最小集合。
7. **反例审查**：有没有"看起来像题型扩展、其实该用别的机制解决"的需求？
   （例如：用户可能真正想要的是"一道题拆成多张卡 + 关联"——而这个应用**已经有**卡片前后置关联，见 §8。）
8. 如果你认为**"题型扩展"整体不该做**（投入产出比不划算、或与产品哲学冲突），请直接说，并说明你建议用户怎么刷题。
