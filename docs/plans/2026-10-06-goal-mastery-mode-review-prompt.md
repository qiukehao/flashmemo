# 闪记 FlashMemo —— 「掌握型今日目标 + 节奏算法」评审请求

> 本文档供外部大模型/评审者使用。**§1~§4 是背景与现状（全部来自真实实现，非设计稿），§5 是我方困惑，§6 是请你回答的问题。**
> 请先读完 §1~§4 再回答；§6 的问题按编号逐条回答即可，不必重写整份文档。

## 0. 一句话问题

用户希望「今日目标」从一种变成两种——**今天要复习 N 张**（已有）与**今天要掌握 N 张**（新增）。
难点不是加个开关，而是要重做**目标驱动的弹窗节奏算法**：现有算法假设"目标是可控的投入（评一张 +1）"，
而"掌握"是**不可控的产出**（评了也未必掌握，且按本应用的定义需要跨 3 个学习日）。
请评审：这个目标该怎么定义、节奏算法该怎么改、不可达时如何降级。

---

## 1. 产品背景

**闪记 FlashMemo**：常驻 Windows 托盘的闪卡复习工具。用户导入 Markdown 八股文笔记建卡；常驻引擎每 15 秒
评估一次，到点在屏幕中央弹出复习窗（每次 1~N 张），用户对每张卡三档评分。

- **硬约束**：核心功能零网络请求、数据只在 `%APPDATA%\FlashMemo`、常驻低占用（内存 ~100MB、空闲 CPU≈0）、
  单实例、开机自启可选。将开源（MIT），作者是备考技术面试的学生 + AI 结对开发。
- **用户画像**：备考者，笔记是 MySQL/Redis/JVM/网络/OS 等八股文，常在**晚上一个固定时段集中复习**。
- **产品哲学（用户明确反复强调）**：**正向表述**——界面只说"已经做了多少"，绝不说"还欠多少"；
  **目标随时段结束作废，永远不变成债务**（原话："完不成也不欠账"）。
  这条哲学是本次设计的关键约束：任何"未达标就加压"的机制都要非常小心。

## 2. 现状：今日目标与节奏算法（当前真实实现）

### 2.1 今日目标（2026-10-04 上线）

用户在首页目标条里设一句话：「今晚 **19:00–22:00** 想复习 **100 张**」。参数存 SQLite KV：
`goal_enabled` / `goal_target` / `goal_start` / `goal_end`。

### 2.2 节奏公式（`src-tauri/src/engine.rs`，每个 15s tick 从零重算）

```
remaining_popups = ceil(remaining_cards / per_popup)          // per_popup 默认 3
interval_minutes = clamp( round( (window_end - now) / remaining_popups ), 3, 60 )

remaining_cards  = goal_target - reviewed_today
reviewed_today   = 学习日内 review_log 的行数      // 三个评分任评一个都算 1 张；「跳过」不写日志、不算
```

设计要点：

- **从零重算**（不用累计、不预测）：落后就自动加密、超前就自动变松，天然自我纠偏；
- **时段外或已达标 → 无目标节奏**，引擎回落到常规弹窗间隔（设置项 `popup_interval_min`，默认 20 分钟）；
- **另有预告值**：`planned_goal_interval` = 把整段时段均匀铺满的间隔，用于时段开始前告诉用户"这个目标大概意味着多久弹一次"；
- 首页目标条显示一行实时节奏文案，15s 轮询跟随，例如
  「当前节奏：约每 15 分钟弹一次 · 一轮 3 张」/ 时段前「计划节奏：约每 5 分钟弹一次 · 一轮 3 张」。

### 2.3 引擎其余闸门（与目标节奏串行叠加，不是替代）

1. **学习时段**（默认 09:00–22:30）外不弹；
2. **弹窗节流**：距上次弹窗不足 `popup_interval_min` 时即使有卡到期也不弹（手动「立即复习」不受限）；
3. **每日弹窗上限**（默认 40，0=不限）：超过后当天只发轻提醒（系统通知），不再弹窗；
4. **娱乐加速 / 学习延后**：检测到在娱乐应用则间隔减半（上限 30% 每日额度），在学习应用则延后；
5. **连续逃避惩罚**：连续 N 次没评分就关窗 → 下次只弹 1 张并把间隔压到 10 分钟。

## 3. 现有「掌握」的严格定义（关键约束，来自真实代码）

本应用**已经**有"掌握"的概念，它是自动归档的判据（`services.rs` / `scheduler.rs`）：

- **一张卡算「掌握」= 连续 `archive_threshold`（默认 3）次评「可以讲出来」，且这几次必须落在
  `archive_threshold` 个不同的学习日**（`speak_days` 按学习日去重；同一天连答三次只记一个 distinct day，
  官方测试名即 `same_day_speakables_never_archive_or_level_twice`：*"one afternoon of recall is not mastery"*）。
- 任何非「可以讲出来」的评分（熟悉/不了解）会把 `speak_streak` 清零，掌握进度回到起点。
- 另有**链式门槛**：一张卡即使自己达标，若它的前置/后置邻居未达标，也暂不归档（"一个弱链接拖住整组"）。
- 另有**每天最多升 1 级**：等级 0~5，等级越高"可以讲出来"后的再出现间隔越长（等级基础间隔 3/5/10/20/50/100 张）。
- **学习日 = 凌晨 4:00 分界**（Anki 惯例），全项目统一（首页统计、目标、连续打卡、热力图、每日上限同一口径）。

**由此得到的硬事实：在这个应用里，一张卡"掌握"至少要跨 3 个学习日。今天不可能把一张今天才开始复习的卡变成"已掌握"。**

## 4. 我理解的用户意图

用户原话："今日目标我希望能够有两个选项，一个设定今天要复习的卡片数量，一个是今天要掌握的卡片数量。
要实现这个就需要你帮我重新优化这个今日目标的间隔排序算法。"

即：**复习型目标**（投入量，已有）+ **掌握型目标**（产出量，新增），并且**节奏算法要跟着改**。

## 5. 我方困惑（开门见山列出来）

### D1. 「今天要掌握 N 张」到底算哪种？（产品语义，必须由用户拍板）

结合 §3 的定义，至少四种解释，行为差异巨大：

| 口径 | 含义 | 池子大小 | 名实相符？ |
|---|---|---|---|
| (a) 推进 | 今天**获得一次**「可以讲出来」的卡数（按卡去重） | 大而稳定 | ✗ 叫"掌握"其实只是"推进了一步" |
| (b) 完成 | 今天**补齐第 3 个学习日 → 真正归档**的卡数 | 极小（只有"已连续 2 天讲出、今天到期"的卡） | ✓ 但多数日子凑不满 N |
| (c) 等级 | 今天等级达到某阈值（如 level≥3）的卡数 | 小（受"每天最多升 1 级"限制，至少 3 天） | 部分 |
| (d) 存量 | 今天**结束时**处于掌握态的卡总数 | — | ✗ 用户一设目标就"凭空完成"一大截，目标形同虚设，应排除 |

### D2. 池子大小不可控 → 目标可能**物理上不可达**，而现有公式会把不可达变成"轰炸"

这是我最担心的一点。现有公式靠"remaining 会下降"来自我纠偏；掌握模式下 remaining 可能**长时间不下降**
（弹了 20 张、一张都没达标），于是：

```
remaining_popups 不变 → 分母不变 → (window_end - now) 越来越小 → interval 越来越小 → 一路压到 3 分钟地板
```

结果就是**目标越不可达，弹得越密**——正好把用户推向逃避（而逃避惩罚又把间隔压到 10 分钟，进一步恶化）。
**这与产品哲学（目标不成债务、正向表述）直接冲突。** 所以"不可达时怎么办"必须有明确策略。

### D3. 产出式目标无法用投入式公式推导

- 复习型：缴入式，`评一张 = +1`，目标与动作一一对应，公式成立。
- 掌握型：产出式，**同样的动作（评分）在不同卡上产出不同**——一张 `speak_streak=2` 的老卡评一次就达标，
  一张新卡评一次只是起点。要把"今天掌握 N 张"翻译成"该多久弹一次"，必须先估计
  **候选池里"离掌握还有多远"的分布**（需要查库统计 `speak_streak` 分布），而不是简单算 `N / per_popup`。

### D4. 两个目标的关系（产品决策）

- 互斥单选，还是可以同时设？
- 若同时设「复习 50 张」+「掌握 30 张」：二者可能**互相冲突**（掌握 30 张可能要弹 80 张，超出复习目标的 50 张）。
  合成规则是什么——取更紧的间隔（`min`）、更松的（`max`）、还是分别算完再给用户看两个数字？

### D5. 计数与去重口径

- 同一张卡今天评了两次「可以讲出来」：复习口径算 2 张，掌握口径该算 1 还是 2？（我倾向掌握口径按卡去重，否则刷同一张卡就能刷满）
- 「熟悉」涨不涨掌握进度？（按 §3 不涨——它清零 `speak_streak`）
- 今天已拿到的掌握进度，若之后评了「不了解」（`speak_streak` 清零），**进度条要不要回退**？
  按"正向表述、只说做了多少"，我倾向记**事件**（不回退），但这会让"掌握"数字与卡的当前状态不一致。

### D6. 与归档/链式门槛的关系

若"掌握"直接等于"归档"，则用户会遇到：**我明确讲出来了、`speak_streak` 也够了，但因为邻居没掌握而不归档 → 不算今天掌握**。
这会让进度条"卡住不涨"，用户无法理解。是否应该把"掌握计数"与"归档"解耦（计数看 `speak_streak`+distinct days，归档另看链式门槛）？

### D7. 长期可持续性

卡片总数有限，已归档的卡退出轮换。若用户每天都要"新掌握 N 张"，**某天所有卡都掌握了怎么办**？
自动视为达成？还是提示"没有可掌握的卡了"？以及归档抽查（spot check）偶尔把归档卡打回复习，会不会让"掌握数"倒退？

### D8. 我倾向的最小可行方案（供评审批判）

先不追求"最优算法"，而是：
1. 目标加 `goal_mode: "review" | "mastery"`，互斥单选；
2. 掌握进度用口径 (a)（今天获得「可以讲出来」且按卡去重），文案明确写"掌握"而不是"复习"；
3. 节奏公式**复用现有公式**，但把 `per_popup` 换成"**预期每轮产出**"——由候选池里 `speak_streak>=threshold-1` 的卡占比估算，
   并给该估计设上下限，避免被小样本放大；
4. **加不可达降级**：若最近 X 轮零产出，则把间隔冻结在某个下限之上（而不是继续收紧），并在目标条上诚实提示
   "今天可掌握的卡不多，先把它们推进一轮"。

请评审这一方案是否成立、第 3 步的估算怎么做才稳、第 4 步的降级策略如何设计才不与"目标不成债务"冲突。

## 7. 约束红线（请在你的建议中遵守）

- **零网络**：不能引入任何在线服务/遥测；算法必须是纯本地、可离线运行。
- **低占用**：引擎每 15 秒 tick 一次，算法单次计算必须极廉价（不能每次全表扫描大库；允许缓存）。
- **可解释**：用户要能看懂"为什么现在弹得密/疏"。黑箱公式不接受。
- **不破坏既有不变量**：单实例、同时只有一个复习弹窗、每次评分立即落库、目标随时段作废。
- **可测试**：核心算法必须是纯函数（现有公式 `goal_interval_from` / `planned_goal_interval` 都是纯函数且有单测），
  新算法同样要能脱离数据库单测。
