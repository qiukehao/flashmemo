## 1. 产品背景

**闪记 FlashMemo**：常驻 Windows 托盘的闪卡复习工具。核心流程：

1. 用户导入 Markdown 八股文笔记（`# 卡包 / ## 章节 / ### 卡片`），或手动建卡；
2. 常驻引擎每 15 秒评估一次，到点弹出复习窗（每次 1~N 张卡），用户对每张卡三档评分：**不了解 / 熟悉 / 可以讲出来**；
3. 调度器决定每张卡下次何时再现（按"隔几张卡"而非"隔几小时"，详见 §2）；
4. 连续多次"不了解"自动标记 ⚠ 专项复习；连续多次"可以讲出来"自动归档。

**硬性约束**：
- 纯本地：核心功能（导入/调度/复习/存储）零网络请求，数据只在 `%APPDATA%\FlashMemo`；
- 常驻低占用：目标内存 ~100MB 以内、CPU 空闲时接近 0；
- 单实例运行；主窗口关闭 = 收进托盘；只有托盘菜单"退出"才结束进程；
- 将开源（MIT），是作者的简历项目，作者为备考面试的应届生 + AI 结对开发；
- 当前状态：M1/M2 功能全部完成，91 个 Rust 测试 + 54 个前端测试全绿，已可真实日用。

**用户画像**：备考技术面试的学生，笔记主要是 MySQL/Redis/网络/OS 等八股文，大量使用 Obsidian 标注块语法。

## 2. 复习算法（当前实现）

### 2.1 核心机制

不按"几小时后复习"，而按"**再出现 N 张其他卡片之后复习**"。每张卡有两个条件**同时满足**才可再现：
1. **张数条件**：全局展示计数器 `review_seq`（应用启动以来所有卡片被展示的总次数）走过了该卡的 `next_eligible_seq`；
2. **时间条件**：过了该评分的时间下限（见 §2.5）。

### 2.2 三档评分规则

| 评分 | 熟练等级变化 | 间隔 | 时间下限 | 连击计数 |
|---|---|---|---|---|
| 不了解 | −1（最低 1） | 连击 1~2 次：**3 张**；第 3 次：**5 张**+标⚠；第 4 次起：**10 张** | 10 分钟 | unknown_streak +1 |
| 熟悉 | **不变**（新卡 0→1） | max(等级间隔， **8**) | 30 分钟 | 双清零 |
| 可以讲出来 | **+1**（最高 5） | max(等级间隔， **20**) | 2 小时 | speak_streak +1，**清除⚠** |

### 2.3 熟练等级阶梯（0~5 级 → 基础间隔）

```
等级:  0    1    2     3     4     5
间隔:  3    5    10    20    50    100 张
```

熟悉与可以讲出来的实际间隔 = max(等级基础间隔， 该评分的保底值 8/20)，因此低等级时保底生效，高等级时阶梯生效。

### 2.4 关键语义

- **熟悉不涨等级**：定位是"记得但要想一下"，只有"可以讲出来"证明掌握；但熟悉会重置不了解连击。
- **可以讲出来清零不了解连击**，并清除 ⚠ 标记；熟悉**故意不清除** ⚠（记得但讲不出来不算掌握）。
- 连击都是**连续**计数：任何其他评分都会清零另一侧的连击。

### 2.5 ⚠ 需要专项复习

- 连续 **3 次**"不了解"（可配置，最低 2）触发：间隔变 5 张 + 标 ⚠；
- **连锁传播**：手动关联的前置/后置卡一并标 ⚠（只传播一跳，防止整章沦陷）；
- 优先级：每次弹窗最多携带 **1 张** ⚠ 卡插队复习；
- 解除：仅"可以讲出来"，或用户在疑难卡页手动解除。

### 2.6 自动归档

- 连续 **3 次**"可以讲出来"（可配置 2~5）→ 卡片自动归档（保留数据与等级，可恢复重新入队）；
- **链式门槛**：有手动关联的卡，归档要求所有直接关联卡也达到同样掌握度（speak_streak ≥ 阈值或已归档），"一个弱链接拖住全组"；
- 4~5 级卡的间隔阶梯在归档前为 50 → 100 张。

### 2.7 弹窗组队顺序（每次弹窗 N 张，用户当前设 3）

```
⚠ 重点回访卡（最多 1 张） → 到期卡（等级 1~2） → 新卡（受配额） → 维护卡（等级 ≥3 补位）
```

配额：新卡每日上限 5、每次弹窗 1；每日弹窗总上限 120（超出降级为系统轻提醒）；学习时段 9:00~22:30（时段外自动弹窗静默，手动触发不受限）；弹窗最小间隔 5 分钟（手动触发绕过）。

### 2.8 边界行为

- **跳过**：不计分，仅推迟（默认 30 分钟后回队，可配 10~120）；
- **新卡**：等级 0，首评后按三档规则走；
- **编辑卡面**不重置调度状态；删除为软删。

## 3. 软件架构

### 3.1 技术栈与进程模型

- **Tauri 2**（Rust 后端 + 系统 WebView2 前端容器），前端 React 18 + TypeScript(strict) + Vite；
- 存储：SQLite（rusqlite bundled），单文件 `data.db`，`PRAGMA user_version` 管理迁移（v1~v4）；
- 窗口：主窗口 + **预创建的隐藏复习弹窗**（复用同一 WebView，规避 Windows 下运行时创建第二个 WebView2 控制器的死锁）+ AI 侧栏子 Webview；
- 常驻引擎：独立线程 15 秒 tick，决策函数为纯函数（可单测）。

### 3.2 后端模块（src-tauri/src/）

| 模块 | 职责 | 设计要点 |
|---|---|---|
| scheduler.rs | 三档评分 → 新等级/间隔/连击/时间下限 | **纯函数**，preview 与 review 共享同一规则，重点单测 |
| db.rs | 连接、迁移 v1~v4、DAO | 迁移幂等；存时间戳一律 RFC3339 |
| services.rs | 业务编排：评分落库、弹窗组队、统计、导入、备份、归档/疑难 | 可独立测试；不依赖 Tauri 类型 |
| commands.rs | Tauri command 层 | **薄壳**：校验 + 委托 services，无业务逻辑 |
| engine.rs | 15s tick：弹窗决策、托盘、立即复习 | `popup_decision` 纯函数：到期数/时段/暂停/间隔/每日上限/强制标志 |
| ai.rs | AI 侧栏子 Webview 管理 | 独立 data_directory 保登录态；命令式开/关/改尺寸 |
| parser.rs / import.rs | Markdown 解析与导入 | 纯函数；幂等更新；空卡包过滤 |
| logging.rs | 文件日志（日轮转保 7 天）+ panic 钩子 | 前端错误经 frontend_log 命令汇入同一文件 |

### 3.3 前端结构（src/）

- pages/：首页、仪表盘、卡包（工作区含 WYSIWYG 编辑器）、设置、导入、疑难卡、添加卡片；
- components/：ReviewPopup（复习弹窗，含 WYSIWYG 编辑与知识铺垫）、AiSidebar；
- lib/：api.ts（invoke 封装）、markdown.ts（渲染：GFM+标注块+高亮+任务列表+脚注）、wysiwyg.ts（DOM↔Markdown 往返）、mockBackend.ts（浏览器调试用内存假后端，动态加载不进正式包）、logger/env/dom 等；
- 弹窗与主窗口同 bundle，按窗口标签分流；浏览器 mock 让前端可脱离 Rust 调试。

### 3.4 数据模型（SQLite）

```
deck(id, name, chain_by_order, created_at)
chapter(id, deck_id, name, order_idx)
card(id, deck_id, chapter_id, title, content_md, state, stability, difficulty,
     due_at, last_review_at, reps, lapses, leech, locally_edited, learning_step,
     source_file, interval_minutes, unknown_streak, speak_streak, needs_attention,
     level, next_eligible_seq, last_seen_seq)
card_link(from_id, to_id)              -- 手动前后置关联
review_log(card_id, rating, state_before, reviewed_at)
settings(key, value)                   -- 全部可调参数 KV
popup_log(opened_at)                   -- 每日弹窗上限计数
```

### 3.5 架构原则（红线）

1. command 层薄壳，业务逻辑放可独立测试的纯 Rust 模块；
2. 前端不碰数据库，一切经 invoke；
3. 调度纯函数化：决策与副作用分离；
4. 每次评分立即落库（断电不丢）；
5. 锁中毒可恢复 + panic 全捕获进日志；
6. 隐私：无遥测无上报，AI 侧栏是唯一联网面。

### 3.6 性能现状

冷启动 <2s；常驻内存 ~50-80MB；空闲 CPU≈0（15s 轮询一次轻量查询）；单用户单文件库，无并发压力；SQLite 总数据量 <10MB 量级。

## 4. 规划中的新功能（需求描述）

### 4.1 屏幕监控加速（拟接入现成开源方案 Patina）

**用户需求**：检测"我正在用浏览器刷娱乐网页 / 开娱乐软件"，此时**加快复习弹窗的频率**（把打断送到眼前）；反过来若在用学习类应用可以维持或放缓。

**信号源**：不自己造轮子，拟参考/接入 **Patina**（github.com/Ceceliaee/patina，MIT，**与本项目同栈：Tauri v2 + Rust + React**，~高 star 活跃维护）：
- 自动记录前台应用，处理空闲/锁屏/休眠边界；
- **浏览器扩展 Patina Web Sync 可识别浏览器网页标题**；
- 应用分类管理（可标"娱乐/学习"）、排除规则、使用限额提醒；
- 数据本地 SQLite。

**FlashMemo 侧待决策**：① 信号接入方式——直接读 Patina 的本地 SQLite（同机文件，schema 耦合）/ 让 Patina 导出+文件监听 / 复用其 `windows` crate 思路自研一个轻量前台窗口轮询（仅匹配用户配置的娱乐应用清单，不存历史）；② 调度响应——检测到娱乐状态时缩短弹窗间隔/提高每日上限的"加速系数"，如何与既有节流（弹窗间隔、每日上限）叠加而不失控；③ 隐私边界——默认关闭、显式开启、只记录"是否在娱乐清单"的布尔信号而不存网页历史。

### 4.2 弹窗关闭策略模式

- **不可关闭模式**：弹窗内必须完成评分才允许消失（Esc/✕/跳过禁用或需确认）；
- **连续关闭升级模式**：检测连续 N 次未评分就关闭弹窗 → 逐级升级应对（如：缩短下次弹窗间隔、弹窗置顶加锁、轻提醒变强提醒）。
- 需要防误伤：崩溃/关机场景不算"逃避"。

### 4.3 组卷（自定义复习会话）

- 用户自定"今天复习多少张、从哪些卡包各抽几张"；
- 抽取策略：到期优先 / 随机 / 最弱优先（等级最低）/ 混合；
- 现有基础：ReviewSession 机制已支持显式卡列表 + "复习选中/复习该包/学新卡"三个入口；
- 待设计：组卷配置 UI、策略函数（应放 scheduler/services 层保持纯函数）、"试卷"是否可保存复用。

### 4.4 预设卡包与卡包市场

- 内置预置卡包（如"操作系统八股""计算机网络"）；
- 卡包市场：下载他人分享的卡包；
- 冲突：与"零网络"红线的张力——需定策略（离线 .deck 文件分享 vs 显式 opt-in 的在线市场）；导入已有幂等与 locally_edited 冲突检测基础；
- 待设计：分享格式（单文件 Markdown 已可用？还是要带元数据的打包格式）、去重与版本、市场审核。
